# v0.30.4 — A closed session's row stays out of its tmux group

A patch release: one fix and tidying behind it. `terminum upgrade` brings it. A patch rather than a
minor: no new screen, and the messages between terminumd and the page keep their form; only their
order changes.

## Fixed

- **A closed session's row could stand for a moment in its tmux group.** When a pane closed,
  terminumd said that it left its project before it sent the list without that pane. It now sends the
  list first, then the projects, so the row just goes. v0.30.3 listed this as known; it is gone in the
  usual case.

Known and left as it is: while a slow host's list is being read (up to about 11 s), a project action
or a page connecting sends the projects first, so in that rare moment the row still stands in its
group, and the selection goes to the group's first session rather than the project's.

## Verified

`make check` passes: Rust tests, clippy, the Panel's browser check, `web/test/e2e_live.mjs` (251), and
the Page's browser checks in Chromium and WebKit, plus `scripts/security_check.sh`.

- A live check against a real terminumd and a private tmux, in Chromium and WebKit, closes real panes
  and watches every drawing of the list: the closed row never stands in a tmux group, and the selection
  moves to the project's first session. A build with the old order fails it in both engines (4 of 251).
  v0.30.3's live check closed its panes too soon after adding them to the project, so it did not reach
  this order; only checks against a fake terminumd covered it then.
- A session added to a project and closed within 5 s: its project leaves `projects.json` and the row
  menu when those 5 s end, with no new list to carry the message. A build that tells the projects only
  with a changed list fails this in both engines (2 of 251).
- Reviewed with /simplify, and its fixes are in. One proposal was rejected: moving the leaving itself
  after the list would judge a member added during a slow read by its 5 s only after that read. The
  reason is in the spec.

`scripts/e2e_remote.py` passes 37/37 against a stand-in host.

Not verified: the owner's own projects and browser; real remote hosts (the same read serves them).
